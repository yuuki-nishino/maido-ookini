# ADR-0008: 在庫は、確定のトランザクションの中で減らし、取り消しは同じバッチで戻す

- 状態: 採用（Accepted）
- 日付: 2026-10-18

## 背景

- 商品ごとに在庫（いまの残り）を持ち（Issue #67。`menu/{id}.stock`）、注文で自動で減らしたい（Issue #68）
- 在庫は「期間」で区切らず、いまの残りを1つ持つ（1時間ごと・1日ごとなど、補充の単位がイベントで変わるため。ユーザーの回答）
- 確定は、もともとオンライン必須のトランザクション（order-confirm.md §5.1）。番号の採番・冪等・墓標（ADR-0004）で、「確定に失敗した注文は、存在しなかったことになる」を守っている
- 取り消し・取り消しを戻すは、オフラインでも受け付ける（`transitionOrder`。調理画面は、待たずに進める）

## 検討した選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| **A** | **確定のトランザクションの中で、注文の商品のメニューを読み、足りるかを確かめてから減らす。取り消しは、注文の状態の変更と、在庫の `increment` を、同じバッチで書く** | 2台が同時に最後の1つを売っても、トランザクションが片方だけを通す（売りすぎない）。注文の作成と在庫の減少が、必ず一緒に書かれる（確定に失敗すれば、在庫も減らない）。取り消しはオフラインでも受け付けられる。確定1回につき、注文の商品の数だけ、読み取り（と、在庫を使う商品の書き込み）が増える |
| B | 在庫を減らさず、その日の注文から「残り」を計算して見せる | 確定の処理を変えない。ただし、売りすぎを防げない。残りを出すために、注文を読み続ける必要があり、読み取りが増える。期間で区切らない在庫と合わない |
| C | 確定のあとに、別の書き込みで在庫を減らす | 確定と在庫の減少が別々になり、片方だけが書かれうる（通信が切れたとき）。売りすぎも防げない |

## 決定

A を採用する。

- **確定**（order-confirm.md §5.1）：注文と番号のカウンターに加え、注文の商品の `menu` をトランザクションで読む。在庫を使う商品（`stock` が数）で、注文の数が残りを超えれば、**何も書かずに止める**（`StockShortError`。code: `stock`）。足りれば、残りを減らし、その行に `stock: true` の印を付けて、注文を作る
  - 足りないときは、注文は作られていない（サーバーの残りで確かめ、書く前に止めた）ので、確かめ直さずに `idle` に戻し、「在庫が足りない」と、足りない商品を知らせる。カートは残す
  - 同じ `orderId` の再確定（再試行・復元）は、注文が既にあれば、それを返す（在庫は二重に減らない）
  - **足りないと判定したときは、同じ `orderId` の注文が登録されていないかを、サーバーで確かめる**（`getDocFromServer`）。時間切れのあとの「もう一度試す」では、裏で続いていた1回目が先に登録され、その在庫の減少を2回目が「足りない」と読むことがあるため（トランザクションの中で投げた例外は、コミットせず、読んだ値の確かめも行われない）。あれば成功、無ければ「在庫が足りない」、確かめられなければ時間切れ（「もう一度試す」「やめる」で確かめる）。PR #72 のレビュー H1
  - メニューの読みは、まとめて行う（重複なし。品目の数だけ往復が増えて、時間切れに近づかないように）
- **取り消し・取り消しを戻す**：注文の状態の変更と、在庫の `increment`（取り消し：+数、戻す：−数）を、**同じバッチ**で書く。対象は、確定で減らした行（`stock: true`）で、いまメニューにあり、在庫を使っている商品だけ（消えた商品に書くと、バッチごと失敗するため。使っていない商品に足すと、在庫を使い始めてしまうため）。どの商品が対象かは、端末のメニュー（購読）で決める
- **残りのマイナス**：取り消しを戻すは、オフラインでも受け付けるため、足りるかを確かめられない。残りがマイナスになってもよいとする（ルールは -99,999 まで許す）。手で入れる値（使い始める・直す・補充）は、0以上に限る（画面とデータアクセス）。マイナスは売り切れとして見せ、数え直して「残りを直す」で合わせる
- **ルール**：在庫の値は `validMenu` で、整数・範囲だけを検査する。**減らした数が、注文の数と一致するかは、ルールでは検査しない**（注文の `items` を `getAfter` で読んで照らし合わせると、評価の上限に当たるおそれがあり、メンバーは信頼する前提のため）

## 結果

- 確定の読み取りが、注文の商品の数（1〜50。ふつうは数件）だけ増える。在庫を使う商品は、書き込みも1件ずつ増える。Spark の無料枠（1日 5万読み取り・2万書き込み）に対して小さい（Issue #68 で相談済み）
- 調理画面は、取り消しのために、メニューを購読する（メニューの読み取りが、その分増える。100件まで）
- 端末のメニューが古い（在庫を使うのをやめた直後・オフラインで溜めた取り消しなど）と、取り消しで戻さない・戻しすぎることがある。在庫を使っていない商品に足すと、その商品が在庫を使い始める（取り消し：+数）・売り切れのように見える（取り消しを戻す：−数）ことがある（`increment` は null に対して数を書くため。ルールでは区別できない）。気づいたら、メニュー画面で「残りを直す」か「在庫を使わない」で合わせる（既知の制約。PR #72 のレビュー M1）
- 調理画面がメニューを読み込む前（開いた直後）に取り消すと、在庫は戻さない（既知の制約）
- 取り消しのバッチが、在庫の都合（メニューが消えていた・残りが範囲を超えた）で失敗したら、在庫は書かずに、状態の変更だけを書き直す（取り消しそのものは失敗させない。PR #72 のレビュー M3）
- 確定の失敗の理由に「在庫が足りない」が加わる（order-confirm.md §6）
