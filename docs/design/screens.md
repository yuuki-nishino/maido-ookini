# 画面設計

画面ごとの、データの取得元・状態・操作・エラー表示。要件は [SPEC.md](../SPEC.md) の6章。
関数は [data-access.md](./data-access.md)、確定フローは [order-confirm.md](./order-confirm.md)。

## 1. 構成

### 1.1 エントリとURL
| URL | エントリ | 認証 | 内容 |
|---|---|---|---|
| `/` | スタッフ（`index.html`） | 必須 | イベント一覧 → イベント内のタブ |
| `/join?e={eventId}` | スタッフ（同じエントリ） | 必須（未ログインならログインへ） | 招待の受け取り |
| `/s?e={eventId}&o={orderId}` | お客様（`customer.html`） | なし | 注文1件の状況 |

- Hosting の rewrite：`/s` → `/customer.html`、それ以外 → `/index.html`
- スタッフ側のURLは、`/`・`/join` のみ。タブ・選択中のイベントは、メモリと `localStorage` で持つ（URLにしない）。ルーティングは、小さな自前の実装（`history` で `/` と `/join` を判別）で足りる

### 1.2 スタッフ画面の全体
```
App
├─ AuthGate（未ログイン → ログイン画面）
├─ JoinPage（/join）
└─ EventGate（イベント未選択 → EventListPage）
   └─ Shell（イベントを選んでいる間、`watchActiveOrders` を常に購読。接続状態・未送信・調理画面の元データ）
      ├─ StatusBar（接続状態・未送信件数・イベント名・メニュー）
      ├─ Tabs: 注文 | 調理 | 売上 | レジ締め | メニュー | イベント
      ├─ ConfirmDialog / Toast（共通）
      └─ 各タブの画面
```

- #15 の時点：タブは、注文・調理・メニュー・イベント。Shell の購読（`watchActiveOrders`）は、EventHome に置いた。（以下は #10 の時点の記録）#10 の時点：イベントの中に、タブ（注文（準備中）・メニュー・イベント）を置いた（`components/Tabs`、`state/tab.ts`。`hei:tab` に保存）。「イベント」タブには、メンバー・招待・ログアウトを置く。Shell（接続状態・`watchActiveOrders`）と、ほかのタブ（調理・売上・レジ締め）は、後のIssueで足す

### 1.3 状態の持ち方
| 種類 | 持ち方 |
|---|---|
| 認証ユーザー、現在のイベント、接続状態、未送信件数、通知 | グローバル（`@preact/signals`） |
| 購読したデータ（メニュー、調理中の注文） | グローバル（signals）。購読は、`lib/data` の `watch*` を呼ぶフックが管理する |
| カート・支払い方法・お預り（注文） | グローバル（signals。`state/cart.ts`）。タブを切り替えても消えないように。再読み込みでは消える（#12） |
| 入力中の値、モーダルの開閉 | 各画面のローカル（hooks） |
| 永続（`localStorage`） | 下記 |

`localStorage` のキー：
| キー | 内容 |
|---|---|
| `hei:currentEvent` | 現在のイベントID |
| `hei:pending:{eventId}` | 保留中の注文（確定フロー。イベントにつき1件。確定のトランザクションを始める前に保存する） |
| `hei:tab` | 最後に開いたタブ |
| `hei:knownEvents` | これまでにサーバーで確かめた、自分のイベントのID（外れたことの検知。data-access.md §8） |
| `hei:clearPending` | 端末のキャッシュの消去待ちの印（`{ since, events }`。data-access.md §8） |
| `hei:clearOnStart` | ログアウトで消せなかったキャッシュを、次の起動時に消す印 |
| `hei:clearFailed`（`sessionStorage`） | このセッションで、キャッシュの消去に失敗した（自動では、もう試さない） |
- `localStorage` が使えない環境でも、動くようにする（読み書きは try/catch）

### 1.4 表示名の引き方
- 注文・レジ締めの `createdBy` / `updatedBy` / `closedBy` は uid。スタッフ画面で名前を出すときは、`members` から `displayName` を引く。引けない（抜けた・削除された）ときは、「（退会済み）」と表示する

## 3. スタッフ画面

### 3.1 ログイン
- ロゴ（イベント注文アプリ「毎度おおきに」。visual.md §4）、タグライン、「Googleでログイン」ボタン（主・大）
- 失敗：ポップアップが閉じられた → 何も出さない。ネットワーク → 「通信できません」。ポップアップがブラウザに止められた → 「ログインの画面が、ブラウザに止められました。ポップアップを許可してから、もう一度押してください」（#5 で追加）。それ以外 → 「ログインできませんでした」
- 起動直後、保存済みのログインを確かめている間は、「読み込み中…」（ログイン画面を一瞬出さない）

### 3.2 イベント一覧
- データ：`watchMyEvents`（取得できないイベントは、一覧に出さない。孤立の掃除の条件は、data-access.md §3.2）
- 表示：イベント名、日付。タップで選択（`hei:currentEvent` に保存）。**オフラインで起動しても、キャッシュにあるイベントを表示する**（サーバーに確認できないことを理由に、一覧から消さない）。`EventGate` が、保存してある現在のイベントを復元するときも、この一覧の取得を待たない
- **削除中のイベント**（`deleting = true`）：名前の横に「削除中」を表示する。開くと、通常の画面（注文など）には入らず、「このイベントは削除の途中です」＋「削除を再開」（オーナーのみ。§3.9 と同じ処理）＋「一覧に戻る」を表示する。オーナーでないメンバーには、「オーナーが削除中です」と表示する（通常の操作は、ルール上も、まもなくできなくなる）
- 0件：「イベントがありません。招待を受けるか、イベントを作成してください」。作成ボタンは、`creators` に登録されたアカウントにだけ有効（作成を試して、`permission-denied` なら「イベントの作成は、許可されたアカウントのみです」）
- ★「許可されているか」を事前に知る方法はない（`creators` は読めない）。ボタンは常に表示し、失敗時に説明する
- 一覧は、親のイベントを1回だけ取るため、**一覧に戻るたびに購読し直す**（ほかの端末での名前の変更・削除中を反映する。#7）。オフラインで、端末にも一覧が無いときは、「イベントがありません」ではなく「通信できないため、イベント一覧を確認できません」
- オフライン（`navigator.onLine`）の間は、「オフラインです。端末に保存してあるイベントだけを表示しています」を出し、作成ボタンを無効にする（data-access.md §3.9）
- 削除中のイベントの「削除を再開」は、イベントの削除（#21）で足す（#7 では、案内と「一覧に戻る」だけ）
- ログアウトでは、`hei:currentEvent` も消す（同じ端末で、別のアカウントが、前の人のイベントを開かないように）。ログインが切れたとき（`currentUser` が `null`）も、一覧を消す（PR #32 のレビュー E2）
- 選んでいるイベントから外れたとき（サーバーで確かめた一覧で、自分の `members` が無い：イベントが消された・外された・別のアカウントでログインした）は、選択を外して一覧に戻す。オフラインでは判断しない（`isSelectionGone`。レビュー E1）
- 一覧の購読が失敗したら、「やり直す」ボタンで購読し直せる。一覧があるときの失敗も、「イベント一覧を更新できませんでした。表示が古い可能性があります」と知らせる（レビュー E3）

**イベントの作成**（一覧の「イベントを作成」から）
- 入力：イベント名（60文字まで）、開始日・終了日（端末の日付の選択。初期値は今日。開始日を終了日より後にしたら、終了日を合わせる）、釣り銭の準備金（空なら0円。全角数字・カンマを受け付ける。上限10,000,000円）。検査は `validateEventForm`（ルールの `validEvent` と同じ条件）
- 「作成する」：オンライン必須（`assertOnline`）。作成したら、そのイベントを選んで中に入る
- 失敗：`permission` → 「イベントの作成は、許可されたアカウントのみです」。`offline` → 「通信が必要です。電波を確認してから、もう一度押してください」。それ以外 → 「イベントを作成できませんでした…」

### 3.3 招待の受け取り（`/join`）
- 流れ：
  1. すでにメンバーか確認する（`members/{自分のuid}` を **`getDocFromServer`** で取得）。`permission-denied` は、「メンバーではない」と判断する（次へ進む）。通信できなければ、「通信が必要です」を表示する。メンバーなら、そのイベントを選択して `/` へ
  2. メンバーでなければ、`joinEvent`（メンバー作成＋招待の削除）を実行。成功ならそのイベントを選択して `/` へ
  3. 失敗（`permission-denied`）→ 「このアカウント（{メール}）では、このイベントに参加できません。招待されたアカウントでログインし直してください。招待の期限（発行から1日）が切れている場合は、オーナーに再発行を頼んでください」＋「別のアカウントでログイン」
- 「別のアカウントでログイン」は、`prompt: 'select_account'` を指定する（無いと、同じアカウントが自動で選ばれる）
- #8 の実装：
  - 未ログインで `/join` を開くと、ログイン画面に「招待を受け取るには、招待されたGoogleアカウントで、ログインしてください」を出す
  - 参加できないときは、**ログイン中のメールアドレス**を出し、「オーナーには、このアドレスをそのまま伝えてください（Gmailの「.」の有無や「+」の別名では、一致しないことがある）」と添える（★M1）
  - 「別のアカウントでログイン」は、ログアウトしてログイン画面に戻す（ポップアップは、ボタンを押した操作の中で開く必要があるため、ログアウトの後に自動では開かない）。URL は `/join` のままなので、ログインし直すと、もう一度確かめる
  - 通信できない・その他の失敗は、「もう一度」と「イベント一覧へ」。`e` の無いリンクは「招待のリンクが正しくありません」
  - 成功（参加・すでにメンバー）したら、そのイベントを選び、URL を `/` に置き換える（履歴を増やさない）

### 3.4 注文
- データ：メニュー（`watchMenu`）
- ローカル状態：
  - `cart: Map<menuId, { name, price, qty, cook? }>`（**カートに入れた時点の名前・価格・調理の要否を保持する**。`cook` は、調理なしのときだけ `false`）
  - `payment`、`tendered`（お預り）、`note`（メモ。#40）、`qr`（#52：手での選択がなければ、カートの中身から自動。`defaultQr`＝調理が必要な商品が1つでもあればオン）、確定フローの状態（order-confirm.md）
- 導出：`total = Σ price × qty`（**カートの保持する価格**。保存される `items` と、必ず一致する）、`change = tendered - total`
- 操作：
  | 操作 | 動作 |
  |---|---|
  | メニューをタップ | 数量 +1（すでにカートにある行は、その行の価格のまま）。売り切れは無効 |
  | 数量の増減・削除 | カートの行で操作 |
  | クリア | 確認なしで空にする（取り消せないが、軽い操作） |
  | 支払い方法 | 現金／PayPay |
  | メモ | 任意の1行（100文字まで）。「辛さ抜き」など。調理画面のカードに出る。**個人の名前など、個人情報は書かない**旨を、入力欄に添える（「調理画面に出ます（お客様の画面には出ません）」。理由は、注文のデータは、注文IDを知っている人が、技術的には読めるため。[ADR-0007](../adr/0007-note-in-order-doc.md)）。クリア・確定の成功で、空になる（#40） |
  | クイック入力 | 「ちょうど」＝合計に置き換える。お金のボタン「+1,000」「+5,000」「+10,000」（1行目、「ちょうど」と並ぶ）・「+10」「+50」「+100」「+500」（2行目）＝**押すたびに、お預りに足す**（#61。`addTendered`）。手で打った値にも足せる。入力が不正なとき・上限（`TENDERED_MAX`）を超えるときは押せない（`addTendered` も、足さずにそのまま返す）。ボタンの並び（`.options`）にも `touch-action: manipulation` を付ける（隙間を連続でタップしても拡大しない）。押し間違えたら「消す」で入れ直す（「1つ戻す」は入れない。実機で押し間違いが多ければ、別のIssueで足す） |
  | 確定 | **カートが空のとき、または `pending` があるときは無効**。確定フローを開始 |
- 現金で、お預りが合計未満のときは、「不足 ¥◯」を赤で表示。確定は可能（後で渡す場合もあるため）
- カートに入れた後で、メニューが変わった場合：
  - 価格が変わった行には、「価格変更あり（現在 ¥◯）」を出し、「現在の価格にする」で、その行を更新できる。何もしなければ、**カートの価格で確定する**
  - 売り切れになった行には、「売り切れ」を出す。確定は、そのまま可能（警告のみ）
  - 削除された品の行も、カートの保持する名前・価格で確定できる
- 価格は、メニュー側で1円以上に限るため、**合計が0円の注文は、起こらない**
- 確定後のモーダル：
  - QRあり：番号（特大）、QR、「閉じる」
  - QRなし：番号、合計、お釣り、「OK」
- 画面の下部に、確定ボタン（大）。合計も大きく表示
- `pending` がある間（前の注文の確認中・「登録されていません」の確認）は、確定ボタンの上に、「前の注文の確認中です」を出し、確認の画面（order-confirm.md の decide / unverifiable）へ誘導する
- #12 の実装：
  - **カート・支払い方法・お預りは、メモリ上の共有の状態（`state/cart.ts`）に置く**（画面のローカルではなく）。「メニュー」タブを見に行って戻っても、カートが消えないようにするため。再読み込みでは消える。イベントを変えたら空にする。QR は、カートの中身から自動で決める（調理が必要な商品が1つでもあればオン、調理なしだけならオフ、空ならオン）。手で変えた選択は、調理の要否が変わる操作（食べ物を足す・消す）か、カートを空にするまで使う。前回の選択は記憶しない（#52）
  - 計算は `lib/domain/order.ts`（`calcTotal`・`calcChange`・`addToCart`・`changeQty`・`lineNotice`・`applyCurrentPrice`・`parseTendered`）。1つの品は99個まで、1注文は50品まで（data-model.md §2.6）。メニューのボタンから超えようとしたときは、メニューの下に知らせる。カートの＋は、99個・売り切れ・メニューから削除された行では押せない（**売り切れ・削除された行は、減らす・消すだけできる**。PR #38 のレビュー C2・C3）
  - **在庫**（#67・#69）：在庫を使う商品のボタンに「残り ◯」（5以下は赤・太字）。**残り0以下は「予約で受付（予約 N）」で、押せる**（予約で受ける。売り切れは、手の `soldOut` だけ。#69）。カートの数量が残りを超えたら、その行に「残りは ◯ です。確定のときに、超える分を予約にするか選べます」（`lineNotice` の `stockShort`）。確定で足りなければ、**画面の中央のダイアログ**（`StockShortDialog`。「在庫が足りません」、商品ごとに「残り N（注文 M・予約になる K）」）で、「数を減らす」（左）・「予約として確定する」（右・主）を選ぶ。ダイアログに「お渡しの目安（任意）」の時刻の欄（`parseEta`：その日の、いまより後の時刻だけ。いまより前は「いまより後の時刻を入れてください」で押せない。#70）（order-confirm.md §5.1・§6。下に出る知らせでは、気づかなかったため）
  - メニューは、`useMenu`（`state/menu.ts`）を、メニュー画面と共有する。タップで追加するボタンは、名前・価格・カートの数（右上の印）。売り切れは押せない
  - お預りは、現金のときだけ出す。クイック入力は、上の表（「ちょうど」＋お金のボタン7つ。#61）。入力は、全角数字・カンマ・「円」を受け付ける（`parseTendered`。上限は、ありうる合計の最大 100,000円 × 99個 × 50品 ＝ 495,000,000円。「ちょうど」が、どの合計でも入るように。レビュー C1）。不足は赤で「不足 ¥◯」
  - 合計と確定のボタンは、画面の下に固定する。カートが空のときは「メニューを選んでください」で押せない。確定の処理は #13、端末に残った確定の途中の記録（`pending`）の復元は #14（order-confirm.md §4・§5.3）。記録がある間は、確定できない

### 3.5 調理
- データ：Shell で購読している `watchActiveOrders` の結果。「済みも表示」を入れたときだけ `watchOrdersOfDay(today)`
- 表示：左「調理中」、右「できあがり」。並び順は **`(day, number)` の昇順**。複数日の開催で、前日の調理中が残っているときは、**今日以外の注文に、日付の印**（例：「10/3」）を付ける
- カード：番号（大）、品目（調理なしの行は、薄くして「調理なし」の印を付ける。#52）、支払い方法、合計、経過分数（`now - createdAt`、1分ごとに更新）
- 操作（カード内）：
  | 状態 | ボタン |
  |---|---|
  | 調理中 | 「完成」（大）、「取り消し」、「QR」、「支払い変更」 |
  | できあがり | 「もう一度呼ぶ」（QRありのみ。#58）、「渡した」（大）、「調理中に戻す」、「取り消し」、「QR」、「支払い変更」 |
  | お渡し済み（済み表示のとき） | 「渡したを戻す」、「取り消し」、「支払い変更」 |
  | 取り消し（済み表示のとき） | 「取り消しを戻す」、「支払い変更」 |
- QRなしの注文は、確定と同時に「お渡し済み」になる。**取り違えは、「済みも表示」を入れて、そのカードの「支払い変更」で直す**
- **既知の制約**：「済みも表示」は、今日の注文だけを読み込む。**前日以前の、お渡し済み・取り消しの注文の支払い方法は、直せない**（前日の注文がまだ調理中・できあがりなら、通常のカードで直せる）（その日の内訳〔現金・PayPay〕とCSVの支払い列は、誤ったまま残る。売上の合計は変わらない）。前日分の取り違えに気付いたら、レジ締めのメモ（`note`）に、「◯番 現金→PayPay ¥500」のように残す（SPEC 4.3）
- 「取り消し」は、確認ダイアログ（「◯番を取り消しますか？」）。他は、確認なし（押し間違いは、戻せる）
- **もう一度呼ぶ**（#58。`RecallButton`、`recallState`〔`lib/domain/recall.ts`〕、`recallOrder`）：お客様が来ないとき、お客様の画面で、声を鳴らし直す（`calls` を +1。data-model.md §3）
  | 状態 | ボタン |
  |---|---|
  | 押せる | 「もう一度呼ぶ」（メガホンのアイコン） |

- **「完成」「渡した」の猶予**（#45）：押すと、カードがすぐ次の状態（できあがり・お渡し済み）に動いて見え、画面の下に「◯番を『できあがり』にしました［元に戻す］」を、**5秒**出す（`UndoBar`。どのタブでも出る。猶予の残りは、帯が縮んで示す）。**この間は、サーバーに書かない**。「元に戻す」で、何も書かずに、元の状態に戻る（お客様の画面は、一度も変わらない）。戻さなければ、5秒後に書く。対象は、「完成」「渡した」だけ

### 3.7 レジ締め
- データ：`fetchOrdersOfDayFromServer(day)`（サーバーから取得。画面を開いたとき・「更新」）と `getClosing(day)`
- **オフラインのときは、サーバーから取得できないため、集計を出さず、「通信できません。レジ締めは、通信できる状態で行ってください」を表示し、「締める」を無効にする**
- 入力：準備金（初期値＝`closing.floatCash` または `event.floatCash`）、数えた現金（手で入れる、または、お金の種類ごとの枚数から計算する。#64）
- **枚数で数える**（#64。`CashCountPanel`、`cashCountView`・`parseCount`〔`lib/domain/closing.ts`〕、`state/cashCount.ts`）：数えた現金の下に、種類ごとの行（金額｜枚数の入力｜枚｜小計）を並べる（`DENOMINATIONS`：10,000・5,000・1,000・500・100・50・10・5・1円。2,000円札は入れない）
  - 枚数は 0〜9,999（`COUNT_MAX`。全角数字・「枚」を受け付ける。前後の空白は消す〔数字の間の空白は、打ち間違いとして通さない〕。空は 0）。不正な行は、枠を赤くし、小計の位置に「0〜9,999枚」
  - **1つでも枚数を入れたら、数えた現金は、枚数の合計**（入力欄は読み取り専用にし、「下の枚数から計算しています」と添える）。手で入れた値は使わない（どちらか一方だけを使い、食い違わないように）。「枚数を消す」（確認ダイアログあり。数えた途中の押し間違いで、全部消えないように）で、手で入れる形に戻る。不正な行がある・合計が上限（10,000,000円）を超えるときは、締められない（差額の欄は「枚数を確かめてください」）。読み取り専用の欄は、地の色・細い枠にして、入力できる欄と見分ける（`TextField` の `readOnly`）。狭い画面（320〜360px）では、小計の列を縮めて、はみ出さないようにする
  - **内訳は保存しない**（締めには、数えた現金の合計だけを残す。ルール・データの形は変えない）。数えている途中の枚数は、メモリ上の共有の状態に、イベントと日付ごとに持つ（ほかのタブを見に行っても消えない。再読み込みでは消える）
- 表示：あるはずの現金（`準備金 + 現金売上`）、差額（一致＝緑、不一致＝赤）、締め済みの場合は、締めた時刻・担当者の表示名（§1.4）、「締め後に変更あり」
- 「締め後に変更あり」は、**保存済みの `expectedCash`** と、**保存済みの `floatCash`** で再計算した値を比べる（入力中の準備金は、使わない）。現金から PayPay への変更と、その逆が、同額で相殺される場合は、検知できない（既知の制約）
- 「締める」：`saveClosing`。上書き可能（上書きの前に、確認なし）
- #17 の実装：
  - タブは「注文 | 調理 | 売上 | レジ締め | メニュー | イベント」。日付の切り替えは、`components/DaySelector`（前日・翌日・日付の入力・今日に戻す。#18 の売上でも使う）
  - 取得は、`fetchOrdersOfDayFromServer`（`getDocsFromServer`。8秒で応答がなければ offline）と `getClosing`（`getDocFromServer`）。画面を開いたとき・日付を変えたとき・「更新」で取得する。オフライン（`navigator.onLine` が false、または取得が offline）のときは、取得せず、集計を出さず、「通信できません。レジ締めは、通信できる状態で行ってください」を出し、「締める」を無効にする
  - 入力：準備金（初期値：その日の締めがあればその準備金、無ければイベントの準備金）、数えた現金、メモ（任意・200文字まで）。金額は、全角数字・カンマ・「円」を受け付ける（`parseCashAmount`。0〜10,000,000円）。**入力の初期値は、最初・日付を変えたとき・締めたあとに、締めの記録から入れ直す。「更新」では、入力中の値を残す**（数えた現金を入れたあとに、「更新」を押しても消えない）
  - 表示：現金売上・PayPay（件数つき）、あるはずの現金（準備金＋現金売上）、差額（一致＝緑・不足／多い＝赤。「差額：一致」「差額：不足 ¥100」のように、文字でも示す）。締め済みなら、締めた日時・担当者（`members` から引く。引けないときは「（退会済み）」）・数えた現金・差額。**締め後に変更あり**は、`closingView` で判定し、警告として、「締めたときのあるはずの現金 → いま」を出す
  - 「締める」（締め済みなら「締め直す」）は、保存済みの準備金ではなく、**入力中の準備金**と、**保存の直前にサーバーから取り直した現金売上**から、あるはずの現金を計算して書く。保存したら、Toast「レジ締めを保存しました」
  - 売上の集計は `summarize`（`lib/domain/summary.ts`）、レジ締めの計算は `lib/domain/closing.ts`（`calcExpectedCash`・`calcDiff`・`diffKind`・`closingView`）

- 招待（オーナー）：メールアドレスを入力 →「招待する」→ 招待リンクと「コピー」。招待中の一覧（メール・期限＝発行から1日）、「再発行」「取り消し」
  - #8 の実装：「イベント」タブ（Shell）ができるまでは、イベントの中の仮の画面に置く（オーナーにだけ出す）。入力の補足に「相手がログインに使うアドレスを、そのまま入れてください」。アドレスは `normalizeInviteEmail`（空白除去・小文字・形の確認）
  - 招待リンクは、イベントにつき1つ（`/join?e=`）。「コピー」と、端末が対応していれば「送る」（Web Share。LINEなど）
  - 期限は「期限：10月6日（火）15:54まで」、過ぎたら「期限切れ（再発行してください）」（1分ごとに表示を更新）。書き込みの直後は「発行中…」
  - 「取り消し」は確認ダイアログを出す。招待・再発行・取り消しは、オフラインでは押せない（オンライン必須）
- 「このイベントから抜ける」（**メンバーのみ**。確認あり）。オーナーには出さない（イベントの削除のみ）
  - #9 の実装：メンバー一覧（オーナーが先。「オーナー」の印、自分には「（自分）」）、オーナーの「外す」、メンバーの「このイベントから抜ける」は、「イベント」タブができるまで、イベントの中の仮の画面に置く。外す・抜けるは確認あり、オンライン必須（オフラインでは押せない）。抜けたら一覧へ。外されたら（購読が `permission`）一覧へ

  - #21 の実装：イベントのタブの「イベントの削除」（オーナーのみ）。「イベントを削除」→ 確認ダイアログ（影響の説明と、イベント名の入力。違えば「イベント名が違います」）→ 進捗（段階の名前と「◯件を削除しました」。「終わるまで、この画面を閉じないでください」）→ 終われば一覧へ。止まったら、理由（通信が必要・途中で止まった・許可されていない）と「削除を再開」（続きから消える。名前の入力は、もう求めない）。削除中のイベントを開いたときの画面（§3.2）にも、オーナーに「削除を再開」を出す
- 「イベントを切り替える」「新しいイベントを作成」（作成フォーム：名前・開始日・終了日・準備金）
- ログアウト：未送信があれば、警告して確認を取る（data-access.md §8）

## 4. お客様画面

### 4.1 データと流れ
1. URL の `e`・`o` を検査（英数字20文字）。不正なら「このQRは正しくありません」
2. `watchOrder(e, o)` を購読（メモリキャッシュのみ。永続化しない）。スナップショットは、純粋関数 `customerView` で、次の状態に判定する

   | 入力（スナップショット） | 状態 | 表示 |
   |---|---|---|
   | まだ何も届いていない | loading | 「読み込み中…」 |
   | `exists()` ＝ false、**`fromCache` ＝ false**（サーバーの結果） | notFound | 「注文が見つかりません。お近くのスタッフへお声がけください」 |
   | `exists()` ＝ false、**`fromCache` ＝ true**（キャッシュの結果。オフライン） | loading（**notFoundにしない**） | 「読み込み中…」。8秒続いたら「通信が不安定です。電波の良い場所で、お待ちください」を追加 |
   | エラー（`unavailable` など） | error | 「通信できません。電波の良い場所で、もう一度開いてください」。購読は、SDKが再接続する |
   | `exists()` ＝ true | active | 下記 |
- active で `fromCache` が続くとき：最終更新時刻の横に、「通信が不安定です」を出す

### 4.2 表示（SPEC 6.7）
- 番号（特大）、バッジ、案内文、明細・合計、最終更新時刻（スナップショットの受信時刻）
- 状況ごとの文言・色は、SPECのとおり（調理中＝黄、できあがり＝緑、お渡し済み＝グレー、取り消し＝赤）
- 「できあがり」へ変わった瞬間：直前の状態が `preparing` で、新しい状態が `ready` のとき（`shouldAlert`）、音（下の「音のお知らせ」。タップのあとだけ）と、`navigator.vibrate?.([200, 100, 200])`。**最初の表示のときは、知らせない**
- 支払い方法・**メモ**・スタッフの情報は、表示しない（#40。メモは、注文の文書に入るため、注文IDを知っている人は、技術的には読める。そのため、入力欄で、個人の名前などを書かないよう注意を添える）

- #16 の実装：
  - **注文のリンクの検査**：`e`・`o` が英数字20文字かを、`parseOrderLink` で見る（不正なら、購読せず、「このQRは正しくありません」）
  - **お客様に渡す項目**：`lib/data/customerOrder.ts` の `toCustomerOrder` が、番号・状況・明細（名前・単価・数量）・合計だけを取り出す。支払い方法・メモ・`createdBy` などは、取り出さない（`CustomerOrder` の型にも持たない）
  - 状態の判定は、`customerView(snapshot, waitedMs)`（`lib/domain/customerView.ts`）。`!exists && fromCache` は、loading のまま（8秒続いたら slow ＝「通信が不安定です」）
  - **できあがりの見せ方**：カードを緑にし、番号・バッジを大きくし、ゆっくり脈打たせる（`prefers-reduced-motion` のときは止める）。音・振動は、直前が調理中のときだけ（`shouldAlert`。最初の表示では、しない）。タブの題名にも「12番 へい、お待ち！」を出す
  - 最終更新時刻は、スナップショットを受け取った時刻（`formatClock`。Asia/Tokyo）。`fromCache` が続くときは、「通信が不安定です」
  - ホーム画面への追加は、求めない（manifest・Service Worker は、お客様画面には無い）
  - 読み込みの待ち時間は、「読み込み中と判定されている間」数える（結果が届いたかではなく、`isWaiting`。オフラインで、キャッシュだけの結果が届いても、8秒で「通信が不安定です」が出る。`startWaitTicker`。PR #44 のレビュー V1）
  - 購読が**終わった**（エラー。権限・無料枠の上限など）ときは、2秒から30秒まで間隔を倍にして、つなぎ直す（`watchOrder`。一時的な圏外では、SDK が自分で再接続するため、エラーは出ない）。表示中の注文は、エラーでも残し、「通信が不安定です」を出す（V2）。**間隔を戻すのは、サーバーの結果（`fromCache` でない）が届いたときだけ**（キャッシュの結果では戻さない。再レビュー R2）。**既知の制約**：権限のエラーなど、つなぎ直しても直らないエラーが続くと、表示中のカードは、古い状態のまま「通信が不安定です」で残り、30秒ごとにつなぎ直す。お客様は、注文のQRを持って、スタッフに声をかけてもらう運用を前提とする
  - **振動の既知の制約**：Chrome（Android）は、ページを**一度もタップしていない**と、振動を無効にする（`navigator.vibrate` は、何もしない）。QRを読み取って、そのまま置いておくお客様には、振動は、届かない。下の「音のお知らせ」のボタンをタップすれば、振動も効く。主の合図は、色・大きな表示・脈打ち・タブの題名で、音・振動は、補助（iPhone は、振動に対応していない）

#### 音のお知らせ（#57）
ブラウザは、一度もタップされていないページでは、音を鳴らせない（自動再生の制限）。お客様に、ボタンを1回タップしてもらう。PWA・プッシュ通知・Service Worker は使わない（§4.3 の軽さ、SPEC §1「作らないもの」）。

- **ボタン**（`chimeButton(status, armed, audioRunning, pending)`、`lib/domain/customerView.ts`）：カードの下に出す
  | 状態 | 表示 |
  |---|---|
  | 調理中で、まだタップしていない（`arm`） | ボタン「できあがりを音で知らせる」（ベルのアイコン）（補足「タップしてください（音量を上げておいてください）」。#58：ページから端末の音量は変えられないため、お客様に上げてもらう） |
  | 調理中で、タップのあと、鳴らせる（`armed`） | ボタンではなく、文字「できあがりを、音でお知らせします」（ベルのアイコン） |
  | タップのあと、鳴らせない状態に戻った（`retry`）。調理中のとき、または、できあがりで、まだ鳴らせていない知らせがあるとき | ボタン「音をオンにし直す」（ベルのアイコン）。できあがりのときは、タップで、その場で声を鳴らす |
  | それ以外（お渡し済み・取り消し・鳴らせたあとのできあがり）（`null`） | 出さない |
- **タップでしていること**（`src/customer/chime.ts`）：
  - 声の `<audio>` を作って読み込みを始め、**消音で一度再生して、すぐ止める**（`unlockChime`）。消音は、止めてから**0.5秒**たってから解く（`UNMUTE_DELAY_MS`）。止めてすぐ解くと、iPhone で、タップのときに声の頭が一瞬聞こえた。鳴らす直前まで解かないと、iPhone の裏で鳴らなかった（#57 の実機の確認）。間をあけて、両方を避けられるかを確かめたが、**0.5秒あけても、iPhone の裏では鳴らなかった**（#58 の実機の確認。タップで音が鳴らないことは保てた）。ただし、一度声を鳴らしたあと、すぐホームに戻って「もう一度呼ぶ」を押すと、裏で鳴った（★A1。一度鳴らしたためか、戻った直後でページがまだ止まっていなかったためかは、確かめていない）。タップの中で再生した `<audio>` は、以後、タップなしで鳴らせる。**聞こえる音は鳴らさない**（実機の確認で、タップのときの音は不要とされた）。消音の再生が拒否されたら、「音をオンにし直す」を出す。iPhone の消音スイッチ（マナーモード）でも鳴らすため、対応する端末（Safari 17〜）では、先に `navigator.audioSession.type = 'playback'` にする
  - **Web Audio（`AudioContext`）は使わない**：実機（iPhone）で、裏から戻ったあと、`AudioContext` が `running` のまま、鳴らしても無音になった（`?debug` の記録で、`running` のまま `play` しても聞こえない）。無音を検知できないため、`<audio>` にした。`<audio>` は、鳴らせなければ `play()` が失敗する（`NotAllowedError`）ので、ボタンを出せる
  - 画面を消えなくする（Screen Wake Lock。`setKeepAwake`）。対応していない端末・取れないとき（電池の節約モードなど）は、何もしない
  - まだ鳴らせていない知らせがあれば、消音にせず、**タップの中で**そのまま鳴らす（iPhone は、タップの中で鳴らし始めると、確実に鳴る）
  - Android の振動も、このタップのあとに効くようになる（ページへの操作が、条件のため）
- **音**：録音した声「へい、お待ち！」（`src/customer/hei-omachi.m4a`。AAC・モノラル・80kbps・約4.5秒・約48KB）を1回と、振動（`[200, 100, 200]`）。**「ピンポン」などの代わりの音は、鳴らさない**（実機の確認で、声だけにするとされた）
  - **タップのあとに読み込む**（`<audio>` の `preload = 'auto'`。iPhone は、タップの中の `play()` のときに読み込む）。お客様画面の最初の読み込み（§4.3 の200KB）には含めない。Vite が `assets/` に、ハッシュ付きの名前で出すため、長く（1年）キャッシュされる。読み込めなければ、間隔を倍にして（2秒〜30秒）、読み込み直す（`load()`）。iPhone は、タップの外の `load()` では、データまで読まないことがあるため、読み込み直すたびに、`play()` を試す（`play()` は、自分で読み込みを待つ。再レビュー M2）
  - 声は、公開リポジトリと Hosting で、誰でも聞ける（作った人の了承済み）。差し替えるときは、同じ名前のファイルを置き換える（前後の無音を切り、下の加工をして、AAC にする：`afconvert -f m4af -d aac -b 80000`）
  - **音量**（#58）：Web ページから、端末の音量は上げられない（iPhone・Android とも）。代わりに、ファイルの**聞こえる大きさ**を上げた（-21.3 → **-11.3 LUFS**。約10dB。最大は -1.2 dBFS。-8.8 LUFS〔音の頭を丸めて、さらに大きく〕も試したが、実機でうるさかったため、こちらにした）。加工は ffmpeg：`highpass=f=120,afftdn=nf=-40,agate=threshold=0.03:ratio=6:attack=5:release=200,equalizer=f=3000:t=o:w=2:g=3,acompressor=threshold=-28dB:ratio=6:attack=3:release=120:makeup=10dB,volume=12dB,alimiter=limit=0.84:attack=1:release=60:level=false`（低音を切り、雑音を抑え、スマホのスピーカーで通る 3kHz あたりを持ち上げ、強弱を詰めて、限界の手前で止める）
- **まだ鳴らせていない知らせ**（`pending`。`nextPendingAlert`）：知らせごとに番号を持つ。調理中 → できあがり、またはお店の「もう一度呼ぶ」（`shouldRecall`：できあがりのまま `calls` が増えた。#58）で、新しい番号にし、声を鳴らし始めたら消す。できあがりでなくなったら（お渡し済み・調理中に戻す・取り消し）、消す
  - 立っている間、**声の読み込み（読み込めた・読み込み直した）・拒否からの回復（タップ）・表示に戻る**のどれかが変わるたびに、鳴らそうとする（`playChime`）。「完成」の時点で声を読み込めていなくても、読み込めた時点で鳴る（できあがりのままなら）
  - **同じ知らせ（番号）は、二度鳴らさない**（裏で鳴らした分と、戻ったときの分が重ならないように）。#57 では「5秒以内は重ねない」だったが、「もう一度呼ぶ」が5秒以内に来ると鳴らないため、知らせの番号で判定するようにした（#58）。鳴らし始める途中（`play()` の結果待ち）に、同じ知らせで呼ばれたら、同じ結果を待つ（途中の再生を「鳴った」とみなして、知らせを消さない。再レビュー M1）。別の知らせなら、途中の再生が終わってから鳴らす
- **「お店からお呼びしています」**（#58。`showRecallNotice`）：お店の「もう一度呼ぶ」が届いたら、カードの中に「お店からお呼びしています」（メガホンのアイコン）を、**30秒**（`RECALL_NOTICE_MS`）出す（呼ばれ直したら、数え直す）。タップしていないお客様にも、文字で分かるように。開き直したとき（最初の表示）には、出さない・鳴らさない
  - 「拒否」（ボタン「音をオンにし直す」を出す）は、`NotAllowedError` のときだけ。読み込めなかったための失敗では、出さない（再レビュー M3）
  - タップの消音の再生が、あとから本当の再生を止めないようにする（`playGen`。再レビュー L1）
  - 振動は、変化の瞬間に、その場で試す（声の読み込み・拒否を待たない。タップしていないお客様も、Android で、ページを触っていれば効く。再レビュー L2）
- **画面を消えなくする間**（`shouldKeepAwake`）：タップのあと、調理中・できあがりの間。お渡し済み・取り消しで、外す（電池のため）。取るのは、いつも1つだけ（取っている途中に、外すことになったら、取れた時点で外す。PR のレビュー）
- **ホームに戻って、また開いたとき**（`visibilitychange` で表示に戻ったとき。タップのあとだけ）：
  - Wake Lock は、裏に回ると、ブラウザが自動で外す。表示に戻ったら、取り直す（`syncAwake`）
  - 裏にいる間に、できあがりになったときは、`pending` が残っているので、表示に戻った時点で鳴らす。拒否されたら（`play()` の失敗）、ボタン「音をオンにし直す」を出し、タップで鳴らす。Android は、裏でも鳴ることがある（鳴れば、戻ったときには、鳴らさない）
  - **実機の確認（#57、iPhone）**：最初の版（Web Audio の「ピンポン」）では、戻ったときに鳴った。Web Audio で声にした版では、戻ったときに鳴らなかった（`running` のまま無音）。`<audio>` に変えた版で、開いたまま・マナーモード・戻ったとき・裏にいる間のどれも鳴った。**最後の版（消音を、鳴らす直前まで解かない）では、裏にいる間は鳴らなくなった**（開いたまま・戻ったとき・マナーモードは鳴る。タップのときに声の頭が聞こえる問題を直すのを優先し、許容とした。消音のまま裏で解くのを、iPhone が許さないためと考えるが、確かめていない）。案内は、#62 で、案内文と囲みに変えた（下の「既知の制約」）。★A1
- **調べるための表示**：URL に `&debug` を付けると、カードの下に、音の状態（タップ・声の読み込み・表示の切り替え・鳴らした時刻・最後まで再生されたか〔`ended`〕・拒否）の記録を出す（実機で、原因を確かめるため。お客様には案内しない）
- **既知の制約**：
  - **予約の案内**（#69。`showReservedNote`）：調理中で予約を含む注文の、番号のカードの中に「在庫を用意しています。用意でき次第、調理します」。目安があれば、その下に大きく「お渡しの目安：14:30ごろ」（#70。日付の判定は、最後に受け取った時刻で。描画の中で、いまの時刻を読まない）
  - **画面を離れると鳴らないことを、お客様に伝える**（#62）：調理中の間、音のボタン（または「音でお知らせします」）の**下**に、囲み（太い枠・角は小さく〔ボタンと見分けるため〕。見出しは太字で、注意のアイコン〔`alert`〕。ベルは、音のボタンと紛らわしいため使わない。説明は、短く、小さめ・薄い色で控えめに〔見出しを主にする。実機の確認〕）で「音でお知らせできるのは、この画面を開いているときだけです」「ときどきこの画面に戻ってきてください。できあがっていれば、そのときお知らせします」（`leaveNote`。`showLeaveNote`）。ボタン → 注意事項、の順に読む。タップの前・あと、どちらも出す（タップのあとこそ、安心して離れやすいため）。できあがり以降は、出さない。常に出ている説明なので、`role` は付けない
    - **目立たせる理由**：読みそびれると、音で知らせてもらえると思って離れ、気づけない（実機の確認で、小さな灰色の文字では目立たないとされた）
    - **言い切り**：裏でも鳴ることはあるが（保証しない）、お客様向けには「開いているときだけ」と言い切る（分かりやすさを優先。SPEC §6.7）
    - **言い方**：「開いたままにしてください」とは頼まない（スマホを見ながら待つのが普通で、ずっと開いたままは難しい）。鳴る条件と、戻れば鳴ること（戻る理由）を伝える。調理中の案内文も、「できあがったら、この画面でお知らせします」にした
  - **保証するのは、画面を開いている間だけ**。ホーム画面・ほかのアプリに移っている間は、iPhone では鳴らない（最後の版。上の「実機の確認」）。表示に戻った時点で鳴らす。案内文は「できあがったら、この画面でお知らせします」と、上の囲み（#62）
  - ページがやり直しになったとき（端末に閉じられた・再読み込み・QRを読み直した）は、タップで解いた状態が消える（ブラウザの決まり）。最初の表示になるので、知らせず、ボタンを、もう一度出す
  - 電波が悪く、声を読み込めないままだと、鳴らない（色・大きな表示で気付けるようにする）
  - `audioSession.type = 'playback'` のため、タップのとき、お客様が聴いている音楽が止まるおそれがある（★A1）
  - 「無音の音を流し続けて、裏でもページを止めさせない」方法は、確実でなく、電池も減るため、使わない

### 4.3 軽さ
- 別エントリ。Preact・Firestore（`onSnapshot` が必要なため、フル版）と、画面のコードだけを読み込む（Auth・スタッフ画面・QR生成・CSVは含まない）
- **初回に読み込むJavaScriptは、gzip後 200KB 以下**にする。**ビルドで計測し、超えたら失敗させる**（`scripts/build.mjs`。`customer.html` が読み込む JavaScript の、gzip後の合計）。#16 の時点で、約135KB（Preact・Firestore〔メモリキャッシュ・`onSnapshot`〕・画面。★F1）
- 画像・Webフォントは使わない（システムフォント）
- `<meta name="robots" content="noindex">`、`Referrer-Policy: same-origin`

## 5. アクセシビリティ・レスポンシブ
- ボタンは44px以上。フォーカスが見える。`prefers-reduced-motion` のときは、アニメーションを止める
- スマホ縦・タブレット横の両方で使える。調理画面の2列は、スマホ縦では、タブで切り替える（調理中／できあがり）
- 色だけに頼らず、文字でも状態を示す
